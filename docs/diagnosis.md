# 故障分析与解决记录

记录日期：2026-10-16。以下结论来自本次设备与网络的对照结果，不将推测当作已经确认的根因。

## 用户可见的现象

UU 远程在 Mac 上显示“无法连接至服务器，请检查网络状态或配置”，持续尝试连接。相同网络里的另一台 Windows 电脑可以正常使用 UU；这台 Mac 改连手机热点也可以正常使用。拔掉网线改用当前网络的 Wi-Fi，问题仍曾复现。

这使排查重点落在这台 Mac 与当前网络的组合上。它并不能完全排除客户端差异，也不能仅凭此证明某种封禁策略。

界面中被控设备的“离线”状态不等同于当前 Mac 无法连接 UU 服务器。应先恢复客户端与服务端的连接，再确认被控端开机、联网并运行 UU。

## 关键对照

| 测试 | 本次观察 | 能支持的判断 |
| --- | --- | --- |
| Mac + 手机热点 | UU 可用 | Mac 并非在所有网络下都失败 |
| Windows + 原网络 | UU 可用 | 原网络不是对所有客户端都无法使用 UU |
| Mac + 原网络有线 / Wi-Fi | 都曾失败 | 不能只归因于有线网卡 |
| 相关域名的普通 UDP DNS 查询 | 超时 | 该查询路径在测试时存在问题 |
| 对公开解析器做 TCP DNS 查询 | 获得公开 IPv4 地址 | 存在可用的替代解析路径 |
| 直接连接目标 IP，发送正常 TLS ClientHello | 握手超时 | 仅更换解析方式仍不足以解释和解决全部问题 |
| 同目标 IP，不带 SNI 的握手对照 | 能继续握手 | 初始握手内容或处理路径可能相关；不能用它替代带域名的证书验证 |
| 保留域名及完整握手消息，只拆分初始 TLS 记录 | TLS 握手与证书验证通过 | 握手记录分段会影响本次网络中的连接结果 |
| UU 使用本地 SOCKS5 适配器 | 用户确认 UU 恢复 | 组合方案在本次实际使用中有效 |

## 如何解决

1. 在 `127.0.0.1:17891` 运行 `uu_connection_proxy.py`。
2. 在 UU 内设置 SOCKS5 代理，保持其他应用的系统网络设置不变。
3. 代理通过 TCP DNS 查询目标服务器地址，绕开本次失败的 UDP DNS 查询路径。
4. 对连接的首条 TLS 握手记录，保留其版本及载荷字节，仅改成两条记录：第一条含 1 字节载荷，第二条含剩余载荷，发送之间等待约 20 ms。
5. 后续数据直接双向转发，TLS 仍在 UU 客户端与官方服务器之间建立。

TLS 握手消息是两条记录载荷的拼接。脚本增加了记录头、改变了记录边界，但没有删改握手消息中的域名、密码套件等内容，也没有替换服务端证书。它没有关闭客户端的证书检查。

## 结论与不确定性

本次观察表明同时存在 DNS 查询路径异常，以及与初始 TLS 握手记录分段相关的连接异常。网络中间设备对握手的解析或兼容行为是一种合理解释，但没有设备侧日志或配置证据，不能确认具体设备、具体策略或责任方。

Windows 与 macOS 客户端可能产生不同的握手内容和分段方式，但本次没有完成跨平台报文逐字节对照，因此这只是解释方向。

本方案是经实际验证的连接适配方案，不是已经修复网络设备本身，也不是所有“UU 无法连接”问题的通用结论。
